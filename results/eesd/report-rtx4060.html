批次化 Early-Exit 自我推測解碼 · 實機量測報告

RTX 4060 Laptop 上的 baseline 與三機制量測（兩輪 + 動態到達）

2026-10-30 · LayerSkip Llama3.2-1B · bf16 greedy · 程式碼 hsungo/thesis @ 2cf951c + 本地修改（未 commit）

結論

  • O3 兩輪都重現：ASPIRE 各自排程在 B ≥ 8 只有 0.58–0.59×（比 AR 慢），每 token 深層次數是 AR 的 1.07–1.60 倍；同步批次只要 0.29–0.46 倍。
  • 固定 batch 下沒有方法能在雜訊之外勝出。M1 單獨的幾何平均最高（1.318×，最好的固定 γ 是 1.301×），但兩個行為完全相同的設定（M3 單獨 vs γ=4）就差了 2.5%，所以 +1.3% 不能算贏。
  • 三機制全開比 M1 單獨差（1.226× vs 1.318×）。M2 在 B=1 頻繁換層、在大 B 只付 probe 成本；M3 和 M1 合用時會在不划算的時候搭載 prefill。
  • 動態到達下 M1 沒有贏過所有固定 γ（計畫書 6.5 的條件未達成）。它的實際表現是「不用調參、總是接近最好的 γ」：飽和吞吐量在最佳值的 1–7% 內，而最佳 γ 換資料集就變（cnn_dm γ=4、gsm8k γ=2）。
  • 這台機器是 kernel launch 受限、雜訊大（同一格兩輪相差中位數 6–10%，最大 42%），結果不能直接代表 4090 + 8B。

2 · 兩輪之間的改動

改動原因效果
校準：t_op 改為 max(空 kernel 迴圈, 由實測單層時間反推)空 kernel 量不到真實層裡每個 op 的 dispatch 開銷成本模型 MAPE 31.0% → 16.9%；換 GPU 自動適應（第一輪就已採用）
校準：先建輸出資料夾--validate 寫 CSV 時資料夾不存在而 crashbug 修正
M3：搭載判斷改為整個 prompt 的成本比較；max_wait 3 → 8（只當 TTFT 上限）舊規則只比一塊，忽略 slot 空等；只放寬 max_wait 時實測 e2e −30%、TTFT 46 → 420–590 msM3 單獨時正確判斷「不划算」，不再損失
動態到達：所有方法共用同一到達率；平均輸出長度改用每個 prompt 跑一次；新增從到達算起的 TTFT原本每個方法用自己的速率；且短請求偏差讓速率高估約 2 倍，所有負載都飽和負載 0.5 / 0.8 真的不排隊、B 會變動；第一次的動態到達結果作廢

檔案：solutions/calibrate.py、prefill.py、engine.py、run_ablation.py、README.md、tests/test_eesd.py（新增 m3_force 讓 CPU 測試繼續覆蓋搭載路徑）。87 個 CPU 測試通過。

5 · 為什麼三機制全開沒有贏

M1 與最佳 γ 打平

固定 batch 時，M1 和同步批次做的是同一種決策（整批決定何時驗證）。實測 M1 每回合每請求確認 3.60 token，γ=4 是 3.65，等於自己收斂成 γ≈4。規劃每步 0.4–0.7 ms，是淺層 step 的 5–10%（計畫書估 1%），在 launch 受限的機器上直接變成時間。

M2 淨效果為負

B ≥ 8 時從未換層（k 一直是 3），只付 probe 成本（probe step 比深層 step 慢約 25%）。B = 1 時換層 10–16 次、probe 44–66 次，每次換層捨棄未驗證的草稿。

M3 與 M1 合用時有害

單獨使用時新規則從不搭載，不造成損失。與 M1 合用時在 B = 8/16 搭載 17–49% 的 prefill，這些格子全部輸給 M1 單獨（例如 gsm8k B=16：1.10 vs 1.32），TTFT 從 46 ms 升到 95–324 ms。推測原因：M1 的回合長度變動大，成本檢查拿到的回合長度估計偏樂觀（尚未驗證）。

6 · 動態到達（Poisson，B ≤ 32，修正後）

到達率是同步 γ=4 飽和請求率的 0.5 / 0.8 / 1.0 / 1.2 倍：cnn_dm 6.06 req/s、gsm8k 10.75 req/s。負載 0.5 與 0.8 時沒有排隊，吞吐量就等於到達率，所以比較每 token 延遲（TPOT）；負載 1.0 以上比吞吐量與含排隊的 TTFT。

計畫書在 4090 上報告 1B 為 6.4%。剩下的誤差主要是筆電量測雜訊與加總形式在 launch 受限時重複計算。

8 · 建議的下一步

  1. 以 M1 為主要方法，先修 M2、M3 再合併：M2 加上換層遲滯，並在 k 穩定時拉長 probe 間隔；M3 的成本檢查改用 M1 規劃中的回合長度，decoding slot 少時不搭載。
  2. 每格至少 3 次重複，量測時關閉 Chrome、Discord：目前格子之間 5–10% 的差異都在雜訊內。
  3. 主實驗回到 4090 + 8B：這台是 launch 受限，M1 的 CPU 開銷和多 bucket 的代價被放大，結論不能直接套用。
  4. 決定成本模型是否改成 max 形式（第 7 節）。
